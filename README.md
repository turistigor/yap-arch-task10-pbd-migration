# Соответствие продукта требованиям data privacy, планирование сложной миграции

Требования:
1. Автоматизировать всю работу таким образом, чтобы компания смогла поддержать пятикратный рост объёма данных и расширение команды.
2. Необходимо усилить безопасность медицинских карт, они содержат конфиденциальные данные, которые необходимо защитить от несанкционированного доступа и утечек.
3. В будущем компания хочет уйти от ручной записи клиентов и перейти на единую систему хранения и управления данными, она объединит журналы приёма пациентов, учёт пациентов и учёт оплаты услуг.
4. Система будет поддерживать мобильное приложение, в котором клиенты смогут самостоятельно записаться к врачу через личный кабинет.
5. Парадигма хранения и учёта конфиденциальных данных должна соответствовать принципам и требованиям законодательства РФ.
6. Снизить риски утечки данных, чтобы увеличить доверие и лояльность клиентов.
7. Интеграция лаборатории анализов с API.
   1. API-контракты должны закрывать и скрывать категории данных, которые явно представляют конфиденциальные данные.
   2. Необходимо предотвратить использование API-контрактов, позволяющих третьим лицам выполнять действия и получать данные внешним пользователям, которые они не должны иметь возможности получить.
   3. Поэтому необходимо выстроить такой подход к работе с данными по умолчанию, чтобы новые интеграции не приходилось перевалидировать.
8. Расширение направления обработки данных 
   1. Заменить трудоёмкую ручную обработку Excel-файлов автоматической.
   2. Создать на основе имеющихся файлов озеро данных, которое позволит автоматизировать построение BI, создание LLM и обучение AI на этих данных с применением ML.
9. Разработка новых систем и миграция:
   1.  портал для клиентов,
   2.  портал для сотрудников ресепшена,
   3.  платёжный шлюз,
   4.  CRM для сбора данных о клиентах,
   5.  интеграцию с лабораторией анализов.

НФТ:
1.  Чувствительная информация безопасно хранится и обрабатывается.
2.  Чувствительные данные своевременно удаляются.
3.  Прекращение обработки персональных данных в случае обращения клиента с соответствующим запросом.
4.  Система должна стабильно работать в условиях расширения бизнеса: компания открывает филиалы, нанимает десятки сотрудников и даёт клиентам возможность работать через мобильное приложение.
5.  Нужно предусмотреть простой и понятный процесс внесение изменений и улучшений в систему.
6.  В конфигурации можно вносить изменения без дополнительных доработок.

MVP:
1. Клиент сможет самостоятельно записаться на приём к специалисту через портал компании
2. Команда ресепшена будет видеть записи на приемы и сможет напомнить про него пациенту и специалисту.
3. Определить категории данных пациентов и разнести их по различным доменам, для каждой категории роли (RBAC) или атрибуты (ABAC), на основании которых сотрудникам будет разрешён доступ к данным.

Финальное состояние:
1. Полностью автоматический процесс записи к специалисту через портал и мобильное приложение.
2. Пациенту приходят оповещения о записи через мобильное приложение или голосового робота.
3. В ответ на оповещение клиент может подтвердить или отменить запись, при этом система отправляет оповещение на ресепшен.
4. В мобильном приложении пациент может просматривать только свои данные (анализы, заключения, договор), у него нет доступа к данным других пациентов.
5. В системе есть возможность помечать тегами данные, которые необходимо защитить.
6. Релиз проверяется в автоматическом режиме на работу с тегированными данными, после чего информация передаётся в систему мониторинга и алертинга.
7. В системе появилась возможность проводить аудит доступа к данным и отслеживать нетипичные действия пользователей, с оповещением команды в случае несанкционированного доступа к данным.
